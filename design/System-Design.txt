Question - 1. React vs Angular
| Criteria          | React (Chosen)                | Angular                           |
| ----------------- | ----------------------------- | --------------------------------- |
| Learning Curve    | Easier                        | Steeper                           |

# 1. Amazon EC2
How it works - You launch a virtual machine and deploy NestJS on it.
|------------------------------------------------------------|
| User -> Load Balancer -> EC2 Instance -> NestJS App        |
|------------------------------------------------------------|

App runs 24x7
---
Costing
Charged based on:

- instance type (CPU/RAM)
- uptime (hour/month)
- storage (EBS)
- bandwidth

Performance

✅ very good (dedicated machine)
✅ no cold starts

Scaling
- use Auto Scaling Group
- scale manually/configured rules

Pros
- full server control
- predictable performance
- good for steady traffic

Cons
- manage OS/server
- patching/monitoring
- pay even idle

Why not chosen -> Too much infrastructure management.

-----------------------

2. Amazon ECS Fargate
How it works -> Deploy Dockerized NestJS container.
|----------------------------------------|
|     User -> ALB -> ECS Container       |
|----------------------------------------|

Container always running.
Costing Based on:
- vCPU
- RAM
- running time

Performance

✅ very good
✅ no cold start

Scaling: Auto scales by -> CPU, memory, request, count

Example: 2 -> 20 containers
Pros
- easy container deployment
- good scaling
- no server management

Cons
- costlier at low traffic
- always running

Why not chosen -> Our traffic is bursty; paying continuously is inefficient.

-----------------------

3. Amazon EKS

How it works -> Managed Kubernetes cluster.
|--------------------------------------------|
|     Load Balancer -> Kubernetes Pods       |
|--------------------------------------------|

Costing Based on:
- cluster fee
- worker nodes
- storage/network

Most expensive.
Performance ✅ excellent

Scaling
               |------------------------|
Kubernetes HPA:|  pods auto-scale       |
               |------------------------|

Pros
- enterprise-grade
- multi-service support

Cons
- complex
- DevOps heavy

Why not chosen -> Too complex for current application.

-------------------

4. AWS Elastic Beanstalk

How it works -> Upload app, AWS deploys to EC2.
|-------------------------|
|     User -> ELB -> EC2  |
|-------------------------|

Costing - Pay for EC2 underneath.
Performance - ✅ good
Scaling - Uses EC2 autoscaling.

Pros - easy deployment
Cons
- limited flexibility
- still server-based

Why not chosen -> Not truly serverless.

------------------

5. AWS Lambda (Chosen)

How it works
|--------------------------------------------|
|    API Gateway -> Lambda -> DynamoDB       |
|--------------------------------------------|

Function runs only on request.
Costing Based on: requests, duration, memory
=> No traffic = no cost

Performance
- ✅ very fast after warm start
- ⚠ cold start possible

Scaling Automatic:
|------------------------------------|
|     100 -> 10,000 concurrent       |
|------------------------------------|

No setup needed.
Pros
- serverless
- auto scaling
- cheapest for burst traffic
- zero maintenance

Cons
- cold starts
- max 15 min runtime

Why chosen - Perfect for short NestJS CRUD APIs.

# Best use cases for Lambda

Use Lambda when app is:
✅ API backend
✅ CRUD app
✅ event driven
✅ webhook handler
✅ notification system
✅ scheduled jobs
✅ burst traffic
✅ MVP/startup

Examples:
* todo app
* ecommerce API
* auth service
* payment webhook
* chatbot backend

Perfect for your project.

# When NOT to use Lambda

Avoid Lambda if:

❌ long-running job (>15 min)
❌ websocket-heavy real-time game/chat (sometimes ECS/EC2 better)
❌ huge video processing
❌ custom OS dependency
❌ always-on background worker

Then use:

- Amazon ECS
- Amazon EC2

Final conclustion


We chose AWS Lambda because our Todo API is short-lived, stateless, and bursty. 
Lambda removes infrastructure management, eliminates load balancer/server costs, 
scales automatically, and charges only per request—making it the 
most cost-effective and operationally simple choice.
